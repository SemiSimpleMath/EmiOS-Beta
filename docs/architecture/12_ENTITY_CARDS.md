# Entity Cards — Architecture

## What it is

Entity cards are structured Markdown-like profiles for the people, places, and things the user knows. One card per entity (e.g. "Jamie", "Dana", "Westview Arts"). Each card carries a short `summary`, an ordered list of `key_facts`, optional `contact_info`, `aliases`, and a back-pointer to the source KG node. Cards are persisted in the `entity_cards` SQLite table, generated by an LLM pipeline that reads the entity's KG neighborhood, edited from a dedicated UI, and injected into agent prompts whenever a card's `entity_name` or alias appears in a chat message. They are the **summarized** companion to the **narrative** wiki pages described in `11_WIKI_GENERATOR.md`.

## EntityCard model

`app/assistant/entity_management/entity_cards.py:49-122` — `EntityCard`. SQLite table `entity_cards`, unique on `entity_name`.

| Column | Type | Purpose |
|---|---|---|
| `id` | TEXT (UUID) | Primary key |
| `entity_name` | TEXT, unique | Canonical lexical trigger (matched against chat for injection) |
| `entity_type` | TEXT | Category — typically `Entity`, sometimes `Person`/`Place`/etc. |
| `source_node_id` | TEXT, nullable | FK-style pointer into `kg_node_metadata` (Node table); the KG anchor |
| `original_description` | TEXT | KG node description as it was at last generation (used as the change-detect key) |
| `original_aliases` | JSON list | Aliases pulled directly from the Node |
| `summary` | TEXT (required) | One-to-two-sentence card body, LLM-generated |
| `key_facts` | JSON list | 3–10 short bullet facts, ordered by importance |
| `relationships` | JSON list | Legacy field — v2 writer leaves empty (facts embed relationship info) |
| `user_relevance_reason` | TEXT | One-liner for the L0 view (why this entity matters to the user) |
| `aliases` | JSON list | Processed aliases (may be edited by the user) |
| `confidence` | FLOAT | Generator confidence; powers `low_confidence` maintenance scan |
| `card_metadata` | JSON dict | Schema v2 envelope: `views.{level0,level1,level2}`, `gating`, `signals`, `provenance` (see `kg_entity_card_pipeline.py:935-1015`) |
| `is_active` | BOOL | Soft-delete flag — inactive cards are hidden from injection and editor by default |
| `usage_count` / `last_used` | INT / DATETIME | Atomic increment + timestamp on each prompt injection |
| `batch_number` / `total_batches` | INT | Provenance from legacy v1 batched generator (v2 leaves NULL) |

Two satellite tables back the model:
- `entity_card_usage` — one row per injection event (agent_name, session_id, query_text). `entity_cards.py:124-156`.
- `entity_card_index` — alias lookup table (lower-cased `index_term` + priority), rebuilt deterministically from `entity_name`, `aliases`, `original_aliases` on every persist via `rebuild_entity_card_index_for_card`. `entity_cards.py:159-190`, `287-331`.

`EntityCardRunLog` (line 970) and `DescriptionRunLog` (line 1053) are append-only run-history tables for incremental scheduling.

## The single-slot generation rule

> **Only one card may be generating at any time, across nightly + bulk + single-card paths.**

Why: the entity-card DB write path (`store_entity_card_in_db` → `rebuild_entity_card_index_for_card` → row replace + index delete/recreate, all in one session) does not survive concurrent writers. Two parallel runs corrupt the index table and lose card_metadata. This is documented in user memory `feedback_no_parallel_card_generation` and the route module docstring.

Where the lock lives:
- `app/routes/entity_cards_admin.py:31` — `_GEN_LOCK = threading.Lock()`.
- Acquired non-blocking by both single-card regen (`api_regenerate_v2_single`, line 188) and bulk regen (`api_regenerate_all`, line 311). Both return HTTP 409 `generation_busy` if the lock is already held.
- Bulk runs spawn a background daemon thread (`_bulk_worker`, line 257) that holds the lock for its entire serial walk and releases in a `try/finally`.
- The nightly pipeline (`run_entity_cards_v2`, `bulk_runner.py:127`) walks candidates sequentially in the foreground inside the routine runner — the routine_manager itself serializes pipeline runs, so it doesn't need to grab `_GEN_LOCK`.

The frontend per-card Regenerate button (`app/static/js/entity_cards_editor.js:198-227`) handles 409 by alerting the user; it does not retry.

> Note: nothing prevents the nightly pipeline from running while the admin UI is mid-bulk. Both serialize internally, but two long runs in flight will silently queue at the DB level. In practice the routine runs at 00:20 and the admin UI is interactive during the day, so collisions are rare.

## Generation paths

There are three production entry points; all of them call the same v2 writer (`generate_and_persist_card`):

1. **Nightly pipeline — `entity_cards_pipeline`**
   `configs/routines.json:118-134`. Daily at 00:20 local. Runs `EntityCardsPipeline` (`app/assistant/pipelines/entity_cards/pipeline.py`) with three steps:
   - `PageRankStep` — recompute node PageRank (selection signal).
   - `GenerateEntityCardsStep` — calls `run_entity_cards_v2(incremental=False)`, **catch-up mode**: walks all candidates but only creates **missing** cards. Existing cards are not overwritten unless their KG description changed (`store_entity_card_in_db` short-circuit at `kg_entity_card_pipeline.py:1022-1029`). Writes audit JSON to `day_dir/entity_cards_generation_results.json` and a `resource_entity_cards_generation_results_latest.json` pointer.
   - `PruneEntityCardsDryRunStep` — produces `entity_cards_prune_dry_run.json`. **Never** deactivates; the apply path is a manual script (`prune_entity_cards.py --apply`).

2. **Bulk regen — `/entity-cards-admin`**
   `POST /entity-cards-admin/api/regenerate_all` (`entity_cards_admin.py:304-371`). Body accepts `card_ids`, `suspicious_only`, or `type` filter. Picks targets, queues serial worker thread, `force=True` so descriptions are rewritten regardless of KG-description equality. Status is poll-able at `/entity-cards-admin/api/status`.

3. **Single-card regen — editor button**
   The `/entity_cards` editor renders a per-card `↻` button (`entity_cards_editor.js:163`) that calls `POST /entity-cards-admin/api/regenerate_v2/<card_id>`. Synchronous: blocks the request until the LLM returns (5–15 s typical), then returns the refreshed card row. Same lock, same 409 behavior.

The legacy `POST /entity-cards-admin/api/regenerate/<card_id>` URL (line 167) forwards to the v2 endpoint — the v1 writer (`_process_node_worker`) is no longer wired into any production path.

## KG link binding

`source_node_id` is set during write (`store_entity_card_in_db`, `kg_entity_card_pipeline.py:1069`, `1087`) to the UUID of the KG `Node` whose label matched the entity. It is the only structural link between a card and its KG anchor.

Behavior when the KG node moves or merges:
- **Description change** — the writer detects this by comparing the current `Node.description` against the stored `original_description`. On mismatch, the card is regenerated automatically (`kg_entity_card_pipeline.py:1030-1033`). Same `source_node_id`.
- **Node deleted** — the card is **not** auto-cleaned. It becomes a dangling card whose `source_node_id` no longer resolves. The `broken_link_scan` maintenance step picks this up and proposes deactivation.
- **Node merged into another node** — the card is not migrated. The label match in `_iter_nodes` will pick up the surviving node on the next nightly run and (if no card exists for that label) create a fresh card. The orphaned card is still detected by `broken_link_scan`.
- **Node re-labelled** — the card is keyed by `entity_name` (unique). A renamed node will produce a second card under the new name on the next run; the old one becomes a dangling card.

There is no automated reconciliation of card↔node identity beyond the maintenance scans. The KG-finding-resolver design (memory `project_kg_finding_resolver_emi_team`) is the planned long-term path; not yet built.

## Admin UI — `/entity-cards-admin`

`app/routes/entity_cards_admin.py`. Template `app/templates/entity_cards_admin.html`. Designed for bulk operations:

- `GET  /entity-cards-admin/api/list` — paginated list with `q`, `type`, `suspicious_only` filter. Returns `total`, `suspicious_total`, and per-card `suspicious: bool`.
- `GET  /entity-cards-admin/api/status` — current `_GEN_STATE` snapshot: `running`, `mode` (`single_v2`|`bulk`), `current_label`, `current_idx/total`, `started_at_utc`, `last_result`, `errors`.
- `POST /entity-cards-admin/api/regenerate_v2/<id>` — synchronous single regen.
- `POST /entity-cards-admin/api/regenerate_all` — async bulk regen, returns immediately with `status: "started"`. Frontend polls the status endpoint to update progress.

UI flow: filter for suspicious cards, queue a regen run, poll status, refresh list when done.

## Maintenance pipeline

`app/assistant/pipelines/entity_card_maintenance_pipeline/pipeline.py`. Routine `entity_card_maintenance_pipeline`, weekly Tuesday 02:00 (`configs/routines.json:358-376`). All steps are pure SQL — no LLM calls. Each step is independent (one failure does not abort the others) and writes findings via `entity_card_maintenance.store.upsert_finding`, which dedupes pending findings on `(finding_type, entity_card_id)` (`store.py:31-88`).

Scan order and contracts:

| Step file | finding_type | priority | suggested_action | Trigger |
|---|---|---|---|---|
| `step_broken_link_scan.py` | `broken_kg_link` | high | `deactivate` | `source_node_id` is set but the Node row no longer exists |
| `step_junk_name_scan.py` | `junk_name` | high | `deactivate` | `entity_name` matches artifact patterns: ≤1 alphanumeric char, or ammo-caliber regex (`.308 ammo`, `9mm ammunition`) |
| `step_blank_content_scan.py` | `blank_content` | medium | `review` | `summary < 20 chars` after strip, OR `key_facts` is empty/null |
| `step_low_confidence_scan.py` | `low_confidence` | medium | `review` | `confidence < 0.5` (skipped if `confidence` is NULL) |
| `step_stale_content_scan.py` | `stale_content` | low | `review` | `Node.updated_at - EntityCard.updated_at >= 30 days` |
| `step_no_link_scan.py` | `no_kg_link` | low | `review` | `source_node_id IS NULL` (most are pre-provenance manual cards) |

Each finding records human-readable `evidence_json` (entity name/type, the specific signal value) so reviewers don't need to cross-query the card table.

## Maintenance review UI — `/entity-card-maintenance`

`app/routes/entity_card_maintenance.py`. Template `app/templates/entity_card_maintenance.html`. Backed by `app/assistant/entity_card_maintenance/store.py`.

`EntityCardMaintenanceFinding` schema (`app/assistant/database/entity_card_maintenance_finding.py`): one row per finding, with status `pending → approved/rejected/snoozed → executed`.

Endpoints:
- `GET  /api/findings` — filter by `status`, `type`, `priority`. Sorted high→medium→low priority, then newest first. Default returns `pending`.
- `GET  /api/summary` — counts grouped by `(finding_type, status)` for the dashboard header.
- `POST /api/action` — single finding. Body `{id, action}` where action is `approve` | `reject` | `snooze` | `regenerate`. `approve` runs the default `suggested_action` (deactivate or review). `regenerate` overrides to a v2 card regen regardless of the original suggestion (so a `blank_content` card whose default was "review" can be re-built without leaving the queue).
- `POST /api/bulk_action` — same actions over `ids: [...]`. Only acts on findings still in `pending` state.
- `POST /api/run` — on-demand pipeline trigger (does not wait for the weekly schedule).

Action execution is in `store.execute_approved_finding` (line 119): `deactivate` flips `EntityCard.is_active = False`; `regenerate` calls `generate_and_persist_card(entity_name, force=True)` (which itself owns the single-slot lock through the nightly + admin contract); `review` is a no-op acknowledgement. Failures are recorded as `execution_notes` and the status is rolled back to `approved` so the reviewer can retry.

> Note: the maintenance store calls `generate_and_persist_card` directly, not through `_GEN_LOCK`. If a reviewer triggers a regen while a bulk run is in flight, the two will not formally collide on the lock — but they will still serialize at the SQLite write barrier. Worth tightening if it ever causes problems.

## Relationship to wiki

Entity cards and wiki pages are two projections of the same underlying KG neighborhood, optimized for different consumers:

| | Entity Card | Wiki Page (`11_WIKI_GENERATOR.md`) |
|---|---|---|
| Form | Structured DB row (summary + facts + contact) | Markdown file with YAML frontmatter + prose body |
| Length | Few hundred chars (`level1` is ~400 chars max) | Multi-section narrative, often pages long |
| Target consumer | LLM agent prompts (auto-injected on lexical match) | Human reader + agents that hydrate full neighborhoods |
| Storage | `entity_cards` SQLite table | Files on disk in `EmiWiki` vault (default `<your-home>/EmiWiki`) |
| Update cadence | Nightly missing-only + on-demand regen | Nightly section refresh (only sections affected by KG changes) |
| Shared upstream | `kg_projection.get_entity_neighborhood`, `render_bullets`, `wiki_section_tagger` | same |

The shared-primitives plan in memory `project_kg_projection_shared_primitives` formalizes this: both generators share the upstream pipeline (neighborhood → bullets → tagger → grouped) and diverge at the writer. Coverage is a Venn — most entities get both, but a small card-only or wiki-only tier is intentional.

## How to add / regenerate / debug

**Manually create a card** — Editor: `/entity_cards` → "Create new". Or `POST /api/entity_cards` with `{entity_name, entity_type, summary, ...}`. Manual cards have `source_node_id=NULL`, will surface in the `no_kg_link` maintenance scan as low-priority `review`.

**Regenerate one card** — Editor row's `↻` button (5–15 s, blocks). Or:
```bash
.venv\Scripts\python.exe -c "from app.assistant.pipelines.entity_cards_v2.card_writer import generate_and_persist_card; generate_and_persist_card('Jamie', force=True)"
```
Bootstrap DI first (`import app.assistant.tests.test_setup`) for standalone scripts.

**Bulk regen suspicious cards** — `/entity-cards-admin`, toggle "suspicious only", click "Regenerate all (filtered)". Watch progress at `/entity-cards-admin/api/status`.

**Trigger nightly pipeline manually** —
```bash
.venv\Scripts\python.exe -c "from app.assistant.pipelines.entity_cards.pipeline import EntityCardsPipeline; print(EntityCardsPipeline().run())"
```

**Run maintenance scan on demand** — `POST /entity-card-maintenance/api/run`. Or instantiate `EntityCardMaintenancePipeline().run()` directly. All findings appear at `/entity-card-maintenance` for review.

**Inspect what the summarizer would see** — call `build_card_inputs(label)` from `card_inputs.py`. The returned `CardInputs` dataclass has `bullets`, `grouped_bullets`, `contact_info`, `taxonomy`, `bullet_count` — diff this against the produced card to localize bugs (was the upstream wrong, or did the summarizer hallucinate?).

**Card not getting injected** — Check (1) `is_active=True`, (2) `entity_card_index` has rows for the alias being matched (`rebuild_entity_card_index_for_card` in a session if not), (3) `entity_catalog` is loaded (it's process-global in-memory; restart Flask if you've manually mutated rows).

**Generation hangs / 409 storm** — `_GEN_LOCK` is held. Check `/entity-cards-admin/api/status` for the running mode; if a process crashed mid-bulk the lock won't auto-release across restarts but is reset on Flask restart since it's a `threading.Lock` on a module global.
