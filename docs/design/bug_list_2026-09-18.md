# Bug list — found while certifying the architecture docs (2026-09-18)

Everything here was found by reading a file end to end in order to document it, then
checking its callers. **Nothing in this list has been fixed.** Each entry says what is
wrong, how it was established, and how bad it actually is.

The documentation errors these reads surfaced are already fixed and are not listed here —
this is code only.

Severity is about consequence, not effort:

- **LIVE** — wrong behaviour reachable today.
- **ROT** — dead or unreachable code that misleads a reader or a future refactor.
- **BANNED-PATTERN** — works, but violates a standing rule in this repo.

---

## LIVE

### 1. `/work` reports the wrong database

`work_objects/ui/blueprint.py` — `api_work_list` returns `{"db": _WORK_DB}`, the
dev-file constant `work_objects/work.db`. But `_get_store()` **prefers the live dayflow
store** (`emi.db`) and only drops back to the dev file when the app is not importable. So
the UI tells you which database you are looking at, and is wrong about it whenever it is
working normally.

Established: read both functions in the same file.
Consequence: someone debugging real work objects believes they are looking at a scratch DB,
or vice versa. Cheap fix; needs a path accessor on the store.

### 2. The batch item writer performs no transition validation

`dayflow_orchestrator/dayflow_item_writer.py` — `write_dayflow_item` validates every state
change against `ALLOWED_TRANSITIONS`. `write_dayflow_items_batch` does not: it upserts via
`on_conflict_do_update` and never calls `_validate_transition`. It also defaults new items
to `important_open`.

This is not a theoretical path. **Triage admissions go through it**
(`triage_persist_node._persist_admitted`), as do planned tasks, plan synopses and the
action-log rows in `post_room_finalize_node`.

Established: read both writers; traced the callers of the batch form.
Consequence: any state the batch path writes bypasses the item lifecycle entirely. CLAUDE.md
says transitions are "enforced by `write_dayflow_item`", which is true and reads as though it
covers all writes.

### 3. Same-status writes skip the transition machine (already known, still open)

`work_objects/store.py` — the transition check runs only when the target status differs from
the current one, so `dispatched → dispatched` bypasses validation. Already recorded as
"dispatch claim is not a fence" and not approved for fixing.

Worth noting here because **two subsystems now deliberately rely on it**: the state_mover
updates `reactivate_at` with a same-status write, and the evaluator folds originating intake
into a goal's content the same way. A CAS claim op would have to keep those working.

### 4a. A reply that arrives after the wait-timeout is silently discarded — CONFIRMED

`ticket_manager.py` — `_ALLOWED_TRANSITIONS[EXPIRED]` is an **empty frozenset**, so `expired`
is fully terminal. `_transition_state_in_session` logs a warning and returns `False`. It does
not raise, and no caller of `mark_accepted` checks the return value in a way the user would
ever see.

The sequence: `_wait_for_ticket_response` times out → `mark_expired(reason="wait_timeout")`
fires immediately → the ticket is EXPIRED while still sitting on the user's screen until its
`valid_until`. The user presses a button, `proposed → accepted` is attempted from `expired`,
refused, and their answer is gone. `result_for_ticket` then reports the ticket as "user not
reached", so nothing anywhere records that a reply existed.

**The dayflow lane is protected by accident of arithmetic**, not by design: the arguments node
passes `valid_hours = ASK_WINDOW_HOURS` (1) and `wait_timeout_seconds = ASK_WINDOW_HOURS *
3600` (also 1 hour), so the block and the validity window end together and the exposed gap is
just the race between the timeout firing and the UI refreshing. A
`proactive_suggestion_update` is published to shrink that race.

**Any caller relying on the defaults is exposed for three hours and fifty minutes** — see 4b.

Established: read `TicketState`, `_ALLOWED_TRANSITIONS`, `_transition_state_in_session`,
`mark_expired`, and the tool's timeout path.
Fix shape: either refuse to expire while `valid_until` is in the future, or permit
`expired → accepted` when the reply timestamp precedes `valid_until`, or have the UI hard-close
the ticket the moment the wait ends. The first is probably right — the tool should not declare
a question dead while it is still on screen.

### 4b. The ticket tool's two timeout defaults disagree

`lib/tools/create_dayflow_ticket/create_dayflow_ticket.py` — `valid_hours` defaults to 4
(the DB validity window) while `wait_timeout_seconds` defaults to 600 (how long the call
blocks). A caller that supplies neither reports "user not reached" after ten minutes while
the question stays on screen for another three and a half hours.

The dayflow lane is safe: `dayflow_switchboard_arguments_node` passes both from
`ASK_WINDOW_HOURS`, and its comment says this is exactly why. **Any other caller is exposed.**

Established: read the tool and the arguments node that compensates for it.

### 5. `created_ticket_id` is recovered by scanning prose

`post_room_finalize_node._persist_action_selector_action_logs` — if `result_payload` has no
`ticket_id`, it searches the result TEXT for the words "ticket" and "Created", then takes the
first whitespace token containing `dayflow_orchestrator_`.

That is a wording-based identity join, which this repo bans outright
(`feedback_no_wording_based_identity`: ids and deterministic joins only). Currently
unreachable because the block is dead (see ROT 3), so it is filed LIVE only in the sense that
it would fire the moment that lane were revived.

## ROT

### 1. `payload.session_id` is written in three places and read by nothing

Written by `work_session.open_session`, by `discharge_node` when passed a session id, and
inherited by every child in `store.add_node`. **No reader anywhere.**

The supervisor it exists for, `sweep_stuck_work_nodes`, was rewritten to a pure subtree-idle
rule and consults no session at all. Two docstrings still asserted that "ownership is a graph
fact the supervisor reads"; those are now corrected, but the writes remain.

Established: searched every reference in `app/` and `work_objects/`.
Decision needed: either restore a reader or drop the writes. Right now it is a durable field
that looks load-bearing.

### 2. Four orphaned session helpers

- `dispatch_sweeper._session_root_dispatched` — **zero callers**, and it belonged to the
  orphaned/frozen supervision that no longer exists.
- `work_session.session_alive` — no production callers (tests only).
- `work_session.session_started_at` / `session_started_at_by_id` — no callers at all.

Only `session_alive_by_id` is live, used by the boot-time ask re-arm.

### 3. `post_room_finalize_node` is roughly 600 lines with no producers

The node is on the live path, but almost all of its work reads blackboard keys that **nothing
sets any more**:

| key it reads | producer |
|---|---|
| `planned_tasks` | none (`state_mover_prep_node` only enriches a list it reads back) |
| `state_mutations` | none (the state_mover stopped emitting them) |
| `state_mutations_persisted_tf` | none (`state_transition_guard_node` was deleted) |
| `plan_synopses` | none |
| `completed_plan_ids` | none |
| `closed_task_ids` | none |
| `action_result_events` | none |
| `active_dispatch_records` | none |

So `_build_planned_task_messages`, `_persist_action_selector_action_logs`,
`_attach_execution_results`, `_close_completed_plans`, `_cancel_tasks`, the plan-synopsis
diffing, and the auto-synopsis safety net are all unreachable. The `acted_on_item_ids` path
is also inert by design — `work_node_dispatch_node` clears that key before handing off.

Established: searched for `update_state_value` on each key across `app/`.
Consequence: this is the single largest block of dead code in the dayflow tick, and it
contains two real ideas worth keeping if the lane is ever revived — the auto-synopsis net for
the "HVAC re-research loop", and the deterministic `changed=false` override. Retiring it
should preserve those deliberately rather than deleting them by accident.

### 4. `register_manager_as_tool` has no callers

`work_objects/work_tools.py` — it would register a manager-as-tool wrapper at runtime. The two
node managers ship as ordinary static tool directories instead.

### 5. `graph_neighbors` is never exposed

`work_objects/tools.WorkGraphTools.graph_neighbors` exists and works, but there is no
`work_graph_neighbors` entry in `_SPECS`, so no agent can call it. The module docstring lists
it among the read tools. Possibly deliberate; flagged because the docstring implies otherwise.

## BANNED-PATTERN

### 1. `_format_compact_outcome` degrades silently instead of failing

`post_room_finalize_node` — on any failure it returns a hedged string:
`"(formatter unavailable; see action_log)"`, `"(formatter errored; see action_log)"`,
`"(formatter returned no data; see action_log)"`. That string is then written into an item's
`execution_result` and read by the planner as though it were an outcome.

The repo's rule is to fail loud, never to substitute a default
(`feedback_no_fallbacks_fail_loud`). The stated intent was to avoid blasting 3KB downstream,
which a raise would also avoid.

### 2. The ticket brief has a keyword-sniff fallback

`create_dayflow_ticket._format_brief` — if `ticket_builder_manager` fails, it classifies the
ticket by searching the brief for "ask", "decide", "choice", "confirm", "whether" and takes the
first 60 characters as the title. Both a fallback and a wording-based decision.

Consequence when it fires: the user gets a ticket titled with a truncated fragment, and the
`decision` vs `advice` classification, which decides whether a reply is even possible, is
chosen by substring match.
