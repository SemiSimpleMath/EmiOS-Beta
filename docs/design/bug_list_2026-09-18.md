# Bug list — found while certifying the architecture docs (2026-09-18)

Everything here was found by reading a file end to end in order to document it, then
checking its callers. **Nothing in this list has been fixed.** Each entry says what is
wrong, how it was established, and how bad it actually is.

The documentation errors these reads surfaced are already fixed and are not listed here —
this is code only.

**Verification pass, 2026-09-18 (Fable 5.1).** Every entry below was re-checked against the
code with fresh searches, widened to all file types and to agent forms, since an agent's
structured output lands on the blackboard with no `update_state_value` call. Result: 13 of 13
stand. Two were overstated (4a's on-screen window, 4b's consequence), one was understated
(4b has callers that cannot set the block timeout at all), two needed wording corrected
(LIVE 2's callers, ROT 3's "no producers"), and one bug was found that was not on the list
(LIVE 6). Each entry carries a `Verified:` line saying what was re-read.

Severity is about consequence, not effort:

- **LIVE** — wrong behaviour reachable today.
- **ROT** — dead or unreachable code that misleads a reader or a future refactor.
- **BANNED-PATTERN** — works, but violates a standing rule in this repo.

## LIVE

### 1. `/work` reports the wrong database

`work_objects/ui/blueprint.py` — `api_work_list` returns `{"db": _WORK_DB}`, the
dev-file constant `work_objects/work.db`. But `_get_store()` **prefers the live dayflow
store** (`emi.db`) and only drops back to the dev file when the app is not importable. So
the UI tells you which database you are looking at, and is wrong about it whenever it is
working normally.

Established: read both functions in the same file.
Verified: `_get_store` lines 48–52 prefer `get_dayflow_work_store()`; line 96 returns `_WORK_DB`.
Consequence: someone debugging real work objects believes they are looking at a scratch DB,
or vice versa. Cheap fix; needs a path accessor on the store.

### 2. The batch item writer performs no transition validation

`dayflow_orchestrator/dayflow_item_writer.py` — `write_dayflow_item` validates every state
change against `ALLOWED_TRANSITIONS`. `write_dayflow_items_batch` does not: it upserts via
`on_conflict_do_update` and never calls `_validate_transition`. It also defaults new items
to `important_open`.

Three live callers, and they differ in what they risk. `ingestion.py` and
`entertainment_advisor_stage.py` create NEW rows, where there is no prior state to validate
against, so the missing check costs nothing there. **`triage_persist_node._persist_admitted`
updates EXISTING rows** — `new → artifact`, with no check. That transition happens to be
allowed, so nothing is violated today; nothing enforces it either. The `post_room_finalize_node`
calls the earlier version of this entry named are dead code (ROT 3).

A second difference from `write_dayflow_item`: the batch upsert **replaces `metadata_json`
wholesale** rather than read-merge-write, so a caller that passes a partial dict silently drops
every key it did not include.

Established: read both writers.
Verified: searched every `write_dayflow_items_batch(` call in `app/` and `work_objects/`
outside tests; read the entertainment stage's call site to confirm it creates rather than updates.
Consequence: one live update path with no enforcement, and a clobber semantics nobody has
documented. CLAUDE.md says transitions are "enforced by `write_dayflow_item`", which is true and
reads as though it covers all writes.

### 3. Same-status writes skip the transition machine (already known, still open)

`work_objects/store.py` — the transition check runs only when the target status differs from
the current one, so `dispatched → dispatched` bypasses validation. Already recorded as
"dispatch claim is not a fence" and not approved for fixing.

Worth noting here because **two subsystems now deliberately rely on it**: the state_mover
updates `reactivate_at` with a same-status write, and the evaluator folds originating intake
into a goal's content the same way. A CAS claim op would have to keep those working.

Verified: `store.py` line 498, `if target != node.status:` guards the `TRANSITIONS` lookup; the
terminal-reason check at line 510 is guarded the same way.

### 4a. A reply that arrives after the wait-timeout is silently discarded — CONFIRMED

`ticket_manager.py` — `_ALLOWED_TRANSITIONS[EXPIRED]` is an **empty frozenset**, so `expired`
is fully terminal. `_transition_state_in_session` logs a warning and returns `False`. It does
not raise, and no caller of `mark_accepted` checks the return value in a way the user would
ever see.

The sequence: `_wait_for_ticket_response` times out → `mark_expired(reason="wait_timeout")`
fires immediately. A reply that lands after that attempts `expired → accepted`, is refused, and
`result_for_ticket` reports "user not reached".

**Corrected on verification — the on-screen window is much smaller than first filed.** The web
popup polls `/api/tickets/pending`, which lists `pending`/`proposed` only, and the tool publishes
`proactive_suggestion_update` on timeout, which triggers an immediate re-fetch. So on the web
UI the ticket disappears on the next refresh, not at `valid_until`. The exposure is the race
between the timeout and that refresh, plus any surface that does not re-render (a Slack or
Telegram message stays in the channel with its buttons).

**Two things the first filing missed make the drop uglier than a race.** `TicketService.respond`
writes `user_text` and `user_action` onto the ticket row *before* attempting the transition, so
the late answer **is persisted, on an expired ticket, and never read** — `result_for_ticket`
only consults `user_text` when the state is a responded one. And the refusal is invisible:
`respond` returns `success=False` with no `error`, the API turns that into `200 {"success":
false}`, and `proactive_popup.js` never checks the flag.

The dayflow lane's own window is consistent by arithmetic: the arguments node passes
`valid_hours = ASK_WINDOW_HOURS` and `wait_timeout_seconds = ASK_WINDOW_HOURS * 3600`, so the
block and the validity window end together.

Established: read `TicketState`, `_ALLOWED_TRANSITIONS`, `_transition_state_in_session`,
`mark_expired`, and the tool's timeout path.
Verified: read `TicketService.respond` in full, the `/api/tickets/respond` and
`/api/tickets/pending` routes, and the popup's `proactive_suggestion_update` handler and
`checkForSuggestions`. Searched for every `.respond(` caller: all three are in `ticket_api.py`.
Fix shape: the tool should not `mark_expired` on wait timeout at all — the ticket's own
`valid_until` already bounds it, and a late reply should land through the same recorder the
boot re-arm uses. Failing that, refuse to expire while `valid_until` is in the future.

### 4b. The ticket tool's two timeout defaults disagree

`lib/tools/create_dayflow_ticket/create_dayflow_ticket.py` — `valid_hours` defaults to 4
(the DB validity window) while `wait_timeout_seconds` defaults to 600 (how long the call
blocks). The dayflow lane is safe: `dayflow_switchboard_arguments_node` passes both from
`ASK_WINDOW_HOURS`, and its comment says this is exactly why.

**Corrected on verification, in both directions.** The consequence is not "on screen for three
and a half hours" — per 4a the ticket vanishes from the web popup on the next refresh. The
real consequence is that **a caller's four-hour question is silently withdrawn after ten
minutes**: the tool expires the ticket at the wait timeout and reports "user not reached",
against a validity the caller explicitly asked for.

And it is worse than "any other caller is exposed": **the tool form has no
`wait_timeout_seconds` field at all** (`tool_forms.py` carries `valid_hours: int = 4` and nothing
for the block), so an LLM-invoked call cannot set it even if it wanted to. Every route that
reaches this tool through a switchboard — master_room's, whose prompt sends "remind me" and
"ask me whether" here, and `entertainment_manager`, which lists it in `allowed_tools` — gets a
600-second ask with a 4-hour label.

Two programmatic callers pass `valid_hours` (camera escalation 4 h, scheduler-conflict ask
48 h) and no block timeout, so they look like the worst cases — but they never reach the
timeout at all. See LIVE 6.

Established: read the tool and the arguments node that compensates for it.
Verified: searched every reference to the tool across `app/`, `configs/` and `work_objects/`;
read `tool_forms.py`; distinguished the callers that invoke the tool's `execute` (which waits
and expires) from the many that call `ticket_manager.create_ticket` directly (which do neither
and are not exposed).

### 5. `created_ticket_id` is recovered by scanning prose

`post_room_finalize_node._persist_action_selector_action_logs` — if `result_payload` has no
`ticket_id`, it searches the result TEXT for the words "ticket" and "Created", then takes the
first whitespace token containing `dayflow_orchestrator_`.

That is a wording-based identity join, which this repo bans outright
(`feedback_no_wording_based_identity`: ids and deterministic joins only). Currently
unreachable because the block is dead (see ROT 3), so it is filed LIVE only in the sense that
it would fire the moment that lane were revived.

Verified: re-read lines 814–824; the block is inside `_persist_action_selector_action_logs`,
whose only caller path depends on `action_result_events`, which has no producer.

### 6. The camera escalation and the scheduler-conflict ask can never create a ticket — NEW

`ring_analysis/camera_dispatcher.py` (line 545) and `subconscious/scheduler_arbiter_persist.py`
(line 220) both call the ticket tool's `execute` with **`ticket_kind: "info"`**. The tool's
`_ui_policy_for_ticket_kind` accepts exactly `notify`, `decision`, `advice` and **raises** on
anything else — and it runs *before* `create_ticket`. The raise is caught by `execute`'s outer
`except`, which returns an error `ToolResult`. So the high-stakes door-event escalation and the
"the arbiter punted, ask the user" ticket both fail every time, with an ERROR log line and no
ticket.

`camera_dispatcher` then makes it invisible: its success test is
`result_type in {...} or (isinstance(data, dict) and not data.get("error_code"))`. The error
result carries `data={}`, an empty dict with no `error_code`, so the second clause is **true**
and the function returns `True`. The caller believes the escalation went out.

**Latent, not yet fired.** Searched all 4,317 retained log files for `Got: 'info'` and for any
`camera_dispatcher` / `arbiter_persist` ticket line: zero. Neither path has executed in any
retained log. It will fail the first time a significant door event or a scheduling conflict
occurs.

Established: read both call sites, the tool's `execute` up to the policy check, and
`_ui_policy_for_ticket_kind`.
Verified: the tool form declares `ticket_kind: str` with no `Literal`, so nothing upstream
rejects `"info"` either.
Fix shape: both callers should pass `notify` (a camera event) or `decision` (a conflict needing
the user's call), and `camera_dispatcher`'s success test should check `result_type == "error"`
rather than the absence of a field that error results never carry.

### Historical, resolved — recorded so it is not re-filed

The enum-stringification rejection (`Got: 'ticketkind.notify'`) appears **hundreds of times**
across seven processes in the logs, sometimes three identical failures in a row on one work
node. All seven processes started before commit 42411b30 landed the `.value` unwrap at 22:54 on
2026-09-16 — including process 10104, whose log is dated the 17th because it kept running, and
which is a test harness besides. The live process (started 2026-09-18 16:45) shows two
successful ticket waits and zero rejections. The fix works; the failures are pre-fix. Those
repeated identical results are, incidentally, exactly the pattern `_render_existing_graph`'s
"ALL IDENTICAL" warning was built to expose.

### 1. `payload.session_id` is written in three places and read by nothing

Written by `work_session.open_session`, by `discharge_node` when passed a session id, and
inherited by every child in `store.add_node`. **No reader anywhere.**

The supervisor it exists for, `sweep_stuck_work_nodes`, was rewritten to a pure subtree-idle
rule and consults no session at all. Two docstrings still asserted that "ownership is a graph
fact the supervisor reads"; those are now corrected, but the writes remain.

Established: searched every reference in `app/` and `work_objects/`.
Verified: a widened search across the orchestrator, control nodes, tools, core tools, dayflow
pipelines and `work_objects/` (py/j2/yaml/json) finds the field read in exactly two places, and
both are the writers deciding what to write — `discharge.py` line 81 compares before stamping,
`store.py` line 455 reads a parent's value to inherit it. No consumer exists. A whole-repo
sweep, every file type, found nothing further: the other hits are unrelated session concepts
(doc, plan, geoguessr and task-creation sessions), a stale agent worktree copy of those files,
and recorded tool-result payloads that only show the field is written in production.

Provenance for the decision: the rewrite's own notes, `scratch/WORK_SESSION_REWRITE_PLAN.md`
and `scratch/WS_REWRITE_PROGRESS.md`, name the intended reader — "orphan = dispatched node
whose payload.session_id [is] not a live session", the sweeper re-key listed as step 5. That
reader was replaced by the subtree-idle rule, and the stamping was never taken out with it.
Decision needed: either restore a reader or drop the writes. Right now it is a durable field
that looks load-bearing.

### 3. `post_room_finalize_node` is roughly 600 lines with no live producers

**Wording corrected on verification.** The first filing said the keys had no producers. They
have exactly one, and it is unreachable: the **retired legacy `strategic_planner`'s agent form**
declares `planned_tasks`, `plan_synopses`, `completed_plan_ids` and `closed_task_ids`, and two
`agents/test/*_repro` forms declare `planned_tasks` and `state_mutations`. No manager config
loads any of those agents. The distinction matters: **re-wiring `strategic_planner` would
silently bring this whole block back to life**, so whoever retires it should retire the agent
form in the same change.

| key it reads | producer |
|---|---|
| `planned_tasks` | only the unwired legacy `strategic_planner` form (`state_mover_prep_node` merely enriches a list it reads back) |
| `state_mutations` | only a test repro agent (the live state_mover form has `node_wakes` and `held_work_nodes`, nothing else) |
| `state_mutations_persisted_tf` | none (`state_transition_guard_node` was deleted) |
| `plan_synopses`, `completed_plan_ids`, `closed_task_ids` | only the unwired legacy `strategic_planner` form |
| `action_result_events`, `active_dispatch_records` | none, anywhere |

So `_build_planned_task_messages`, `_persist_action_selector_action_logs`,
`_attach_execution_results`, `_close_completed_plans`, `_cancel_tasks`, the plan-synopsis
diffing, and the auto-synopsis safety net are all unreachable. The `acted_on_item_ids` path
is also inert by design — `work_node_dispatch_node` clears that key before handing off.

Established: searched for `update_state_value` on each key across `app/`.
Verified: re-searched each key with any quoting and any setter idiom across py/j2/yaml, then
listed every field of every live dayflow agent's `agent_form.py` — none of the eight appears —
and confirmed no manager YAML names the legacy planner or the repro agents.
Consequence: this is the single largest block of dead code in the dayflow tick, and it
contains two real ideas worth keeping if the lane is ever revived — the auto-synopsis net for
the "HVAC re-research loop", and the deterministic `changed=false` override. Retiring it
should preserve those deliberately rather than deleting them by accident.

## BANNED-PATTERN

### 1. `_format_compact_outcome` degrades silently instead of failing

`post_room_finalize_node` — on any failure it returns a hedged string:
`"(formatter unavailable; see action_log)"`, `"(formatter errored; see action_log)"`,
`"(formatter returned no data; see action_log)"`. That string is then written into an item's
`execution_result` and read by the planner as though it were an outcome.

The repo's rule is to fail loud, never to substitute a default
(`feedback_no_fallbacks_fail_loud`). The stated intent was to avoid blasting 3KB downstream,
which a raise would also avoid.

Verified: re-read lines 119–180. Note this helper is **live** — `master_room_tool_caller`
imports it — so unlike most of this file the stubs can reach a real item's `execution_result`
on the master_room dispatch path.

### 2. The ticket brief has a keyword-sniff fallback

`create_dayflow_ticket._format_brief` — if `ticket_builder_manager` fails, it classifies the
ticket by searching the brief for "ask", "decide", "choice", "confirm", "whether" and takes the
first 60 characters as the title. Both a fallback and a wording-based decision.

Consequence when it fires: the user gets a ticket titled with a truncated fragment, and the
`decision` vs `advice` classification, which decides whether a reply is even possible, is
chosen by substring match.

Verified: re-read lines 224–235.
