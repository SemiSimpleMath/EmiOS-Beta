### 2. The batch item writer performs no transition validation — FIXED (16af8e84)

Existing rows are read-merge-written and a state change goes through `_validate_transition`,
matching the single writer. One SELECT per batch, not per item. Payload validation moved
ahead of the transaction so a bad batch writes none of itself. Five tests, including the
`new → artifact` move triage actually makes and the same-state write the state_mover needs.

`dayflow_orchestrator/dayflow_item_writer.py` — `write_dayflow_item` validates every state
change against `ALLOWED_TRANSITIONS`. `write_dayflow_items_batch` does not: it upserts via
`on_conflict_do_update` and never calls `_validate_transition`. It also defaults new items
to `important_open`.

Three live callers, and they differ in what they risk. `ingestion.py` and
`entertainment_advisor_stage.py` create NEW rows, where there is no prior state to validate
against, so the missing check costs nothing there. **`triage_persist_node._persist_admitted`
updates EXISTING rows** — `new → artifact`, with no check. That transition happens to be
allowed, so nothing is violated today; nothing enforces it either. The `post_room_finalize_node`
calls the earlier version of this entry named are dead code (ROT 3).

A second difference from `write_dayflow_item`: the batch upsert **replaces `metadata_json`
wholesale** rather than read-merge-write, so a caller that passes a partial dict silently drops
every key it did not include.

Established: read both writers.
Verified: searched every `write_dayflow_items_batch(` call in `app/` and `work_objects/`
outside tests; read the entertainment stage's call site to confirm it creates rather than updates.
Consequence: one live update path with no enforcement, and a clobber semantics nobody has
documented. CLAUDE.md says transitions are "enforced by `write_dayflow_item`", which is true and
reads as though it covers all writes.

### 4a. A reply after the wait-timeout is silently discarded — FIXED (3d068265)

`TicketManager.can_transition` is the read-only half of the state machine, so `respond`
checks before it writes: nothing is saved, nothing is published, and the result carries a
typed `not_answerable` flag. The API answers 409 and the popup stops rolling back the
optimistic removal, showing a notice instead. **It does not recover the answer** — by then
the call has returned "user not reached" and the finalizer has judged the node, so
`result_recorder` would refuse a second outcome regardless. The reply is lost either way;
it is now visibly lost. Whether the tool should expire its ticket at wait-timeout at all is
a lifecycle decision and is HELD.

Found while pinning it: PENDING is displayable but cannot reach ACCEPTED, so a ticket left
in PENDING would be shown and then refuse the answer. Unreachable only because all eleven
`create_ticket` callers happen to call `mark_proposed`, which that function's docstring
calls the caller's responsibility. Pinned by a test, not fixed.

Two of my own assumptions were wrong and the tests caught both: `pending` and `snoozed` do
not accept a reply. Only `proposed` does.

#### Original finding, kept for the reasoning

`ticket_manager.py` — `_ALLOWED_TRANSITIONS[EXPIRED]` is an **empty frozenset**, so `expired`
is fully terminal. `_transition_state_in_session` logs a warning and returns `False`. It does
not raise, and no caller of `mark_accepted` checks the return value in a way the user would
ever see.

The sequence: `_wait_for_ticket_response` times out → `mark_expired(reason="wait_timeout")`
fires immediately. A reply that lands after that attempts `expired → accepted`, is refused, and
`result_for_ticket` reports "user not reached".

**Corrected on verification — the on-screen window is much smaller than first filed.** The web
popup polls `/api/tickets/pending`, which lists `pending`/`proposed` only, and the tool publishes
`proactive_suggestion_update` on timeout, which triggers an immediate re-fetch. So on the web
UI the ticket disappears on the next refresh, not at `valid_until`. The exposure is the race
between the timeout and that refresh, plus any surface that does not re-render (a Slack or
Telegram message stays in the channel with its buttons).

**Two things the first filing missed make the drop uglier than a race.** `TicketService.respond`
writes `user_text` and `user_action` onto the ticket row *before* attempting the transition, so
the late answer **is persisted, on an expired ticket, and never read** — `result_for_ticket`
only consults `user_text` when the state is a responded one. And the refusal is invisible:
`respond` returns `success=False` with no `error`, the API turns that into `200 {"success":
false}`, and `proactive_popup.js` never checks the flag.

The dayflow lane's own window is consistent by arithmetic: the arguments node passes
`valid_hours = ASK_WINDOW_HOURS` and `wait_timeout_seconds = ASK_WINDOW_HOURS * 3600`, so the
block and the validity window end together.

Established: read `TicketState`, `_ALLOWED_TRANSITIONS`, `_transition_state_in_session`,
`mark_expired`, and the tool's timeout path.
Verified: read `TicketService.respond` in full, the `/api/tickets/respond` and
`/api/tickets/pending` routes, and the popup's `proactive_suggestion_update` handler and
`checkForSuggestions`. Searched for every `.respond(` caller: all three are in `ticket_api.py`.
Fix shape: the tool should not `mark_expired` on wait timeout at all — the ticket's own
`valid_until` already bounds it, and a late reply should land through the same recorder the
boot re-arm uses. Failing that, refuse to expire while `valid_until` is in the future.

### 4b. The ticket tool's two timeout defaults disagree — PARTLY FIXED (c0af0690)

`wait_timeout_seconds` is now in the tool form and the contract, so a routed call can set
it, and the tool logs a warning naming both numbers when the block is shorter than the
validity window. **Defaults and the expire-on-timeout behaviour deliberately unchanged:**
deriving the block from `valid_hours` would make the scheduler-conflict ask block a thread
for 48 hours, which is worse than the bug.

**Root cause RESOLVED (3348a2c9), by decision.** The tool conflated *creating* a ticket with
*waiting* for the answer, and the two fire-and-forget callers got a ten-minute block they
never asked for. The tool now takes `wait`, default true so the dayflow lane is untouched,
and both callers pass false. Owner picked this over the two alternatives.

That block was doing real harm once the `"info"` bug was fixed, because the camera
escalation runs inside an event routine: 600s of blocking tripped the routine watchdog's
120s soft limit, producing a spurious "this routine is stuck" ticket during an emergency,
and then expired the emergency ticket at ten minutes against its four-hour validity.

`lib/tools/create_dayflow_ticket/create_dayflow_ticket.py` — `valid_hours` defaults to 4
(the DB validity window) while `wait_timeout_seconds` defaults to 600 (how long the call
blocks). The dayflow lane is safe: `dayflow_switchboard_arguments_node` passes both from
`ASK_WINDOW_HOURS`, and its comment says this is exactly why.

**Corrected on verification, in both directions.** The consequence is not "on screen for three
and a half hours" — per 4a the ticket vanishes from the web popup on the next refresh. The
real consequence is that **a caller's four-hour question is silently withdrawn after ten
minutes**: the tool expires the ticket at the wait timeout and reports "user not reached",
against a validity the caller explicitly asked for.

And it is worse than "any other caller is exposed": **the tool form has no
`wait_timeout_seconds` field at all** (`tool_forms.py` carries `valid_hours: int = 4` and nothing
for the block), so an LLM-invoked call cannot set it even if it wanted to. Every route that
reaches this tool through a switchboard — master_room's, whose prompt sends "remind me" and
"ask me whether" here, and `entertainment_manager`, which lists it in `allowed_tools` — gets a
600-second ask with a 4-hour label.

Two programmatic callers pass `valid_hours` (camera escalation 4 h, scheduler-conflict ask
48 h) and no block timeout, so they look like the worst cases — but they never reach the
timeout at all. See LIVE 6.

Established: read the tool and the arguments node that compensates for it.
Verified: searched every reference to the tool across `app/`, `configs/` and `work_objects/`;
read `tool_forms.py`; distinguished the callers that invoke the tool's `execute` (which waits
and expires) from the many that call `ticket_manager.create_ticket` directly (which do neither
and are not exposed).

### 6. The camera escalation and the conflict ask never created a ticket — FIXED (072c2176)

`notify` for the camera event, `decision` for the conflict. The camera success test now
reads `result_type` instead of looking for an `error_code` field that error results never
carry. Pinned by an AST walk over both modules plus two tests of the success path.

`ring_analysis/camera_dispatcher.py` (line 545) and `subconscious/scheduler_arbiter_persist.py`
(line 220) both call the ticket tool's `execute` with **`ticket_kind: "info"`**. The tool's
`_ui_policy_for_ticket_kind` accepts exactly `notify`, `decision`, `advice` and **raises** on
anything else — and it runs *before* `create_ticket`. The raise is caught by `execute`'s outer
`except`, which returns an error `ToolResult`. So the high-stakes door-event escalation and the
"the arbiter punted, ask the user" ticket both fail every time, with an ERROR log line and no
ticket.

`camera_dispatcher` then makes it invisible: its success test is
`result_type in {...} or (isinstance(data, dict) and not data.get("error_code"))`. The error
result carries `data={}`, an empty dict with no `error_code`, so the second clause is **true**
and the function returns `True`. The caller believes the escalation went out.

**Latent, not yet fired.** Searched all 4,317 retained log files for `Got: 'info'` and for any
`camera_dispatcher` / `arbiter_persist` ticket line: zero. Neither path has executed in any
retained log. It will fail the first time a significant door event or a scheduling conflict
occurs.

Established: read both call sites, the tool's `execute` up to the policy check, and
`_ui_policy_for_ticket_kind`.
Verified: the tool form declares `ticket_kind: str` with no `Literal`, so nothing upstream
rejects `"info"` either.
Fix shape: both callers should pass `notify` (a camera event) or `decision` (a conflict needing
the user's call), and `camera_dispatcher`'s success test should check `result_type == "error"`
rather than the absence of a field that error results never carry.

tests pass across `test_reply_concern_context`, `test_concern_propagation`,

### R1. Routing validation admits names that cannot be activated — PARTLY FIXED locally; mandatory-signal design remains

Intended guarantee: construction proves route targets exist and return-control
signals have routes. Actual: `MultiAgentManager._validate_strict_routing_config`
unions role-binding keys AND values into `routable`, without checking that targets
were loaded. It checks prefixes only for return-control keys already supplied.
`AgentLoader` loads only the declared agent/node entries; `resolve_role_binding`
performs one lookup and `_run_loop` then asks the registry for that instance.
A missing instance or edge is therefore still a runtime failure. Optional
`tool_return`, `critic`, and `summary` blocks skip subsection checks when non-dicts.

Evidence: full reads of manager, loader, Delegator, factory and agent validator;
an isolated execution of the actual validation method accepted
`role_bindings={alias: missing}` with `state_map={planner: alias}` and no
`planner_return_control` edge. Boot's unused-agent check is a reference scan,
not graph reachability. Proposed repair: validate resolved targets against loaded
instances and distinguish mandatory signal edges from optional ones.

### R2. Default error exit is labeled final_answer — FIXED locally

Intended guarantee: aborts are distinguishable from completions by result type.
Actual: `handle_default_error_exit` returns `final_answer`, error prose, and
`data_list=[{}]`, without structured abort data. It is reached when graceful-exit
handling cannot finish. Cancellation and a successful graceful abort report do

Evidence: full manager and exit-node reads; isolated execution of the actual
fallback method confirms its type and missing structured abort payload. Proposed
repair: give every failed exit a consistent abort envelope and check consumers
before changing the result contract.

### R3. Mailbox queues can survive an ended invocation — FIXED locally

Intended guarantee in the comments: unregister and TTL prevent lingering queues.
Actual: unregister clears the queue once. `Mailbox.post` does not check liveness,
so a later post recreates it. TTL is checked only by `drain`; `peek_count` does not
prune and there is no expiry worker in this module. An ended id will normally
never be drained again.

Evidence: full mailbox, registry and invoker reads; isolated execution of the real
Mailbox class confirms post-after-clear recreation and TTL enforcement only on
drain. Proposed repair: make queue closure/posting coordinate with invocation
lifecycle, or add explicit expiry reclamation. Preserve legitimate steering
posted while long synchronous tool calls are running.

### R4. Tool visibility filtering is weaker than its comments promised — FIXED locally

Intended guarantees: the narrower sees only permitted candidates, and visible
means executable under the task's restrictions. Actual in
`ToolScopeService.initialize_scope`:

- `ranked_for_narrower` is copied before scope filtering; `_run_narrower` receives
  that copy. The final visible output IS filtered by scope afterwards, so this
  finding does not establish unauthorized tool execution.
- The ranked path filters scope allow/block and authority, but does not separately
  apply `task_allowed_tools` / `task_except_tools`. ScopeAdapter projects those
  restrictions into request data; ToolCaller checks them at execution. A tool can
  therefore be shown and subsequently refused. A non-empty precomputed visible
  list takes a different path through ingress filtering.

Evidence: full scope adapter, visibility service, manager and ToolCaller reads.
Proposed repair: apply the effective task/scope policy to candidate input and final
visibility, preserving the distinction between relevance ranking and permission.

### R5. Mixed final-answer forms lose sibling domain fields — FIXED for matching terminal envelopes; limitations below

Intended guarantee in the developer recipe: a form containing both `outcome` and
`final_answer_*` returns the domain outcome to programmatic consumers. Actual:
FinalAnswerNode and ManagerExitNode prefer their constructed `final_fields` dict
when an envelope field is populated. Carry-through adds summary/pod references,
but arbitrary siblings such as `outcome` and `revision_log_id` are not copied.
`final_answer_raw` stores that selected payload, so it does not restore siblings.
ManagerExitNode's terminal-agent capture only runs when final fields are absent.

Evidence: full reads of both exit nodes, FinalAnswerNormalizer, manager exit
handling, and the example `kg_mutation/final_answer/agent_form.py`. Proposed
repair: retain the winning agent's full structured output separately from the
human envelope, with tests for mixed forms and stale earlier-agent results.
Current documentation tells callers to verify the returned shape and use explicit
final-answer data items or a domain-only terminal form when needed.

### R6. Budget checks can override completion at the boundary — FIXED locally

Intended behavior to review: a successful last permitted activation should be able
to finish. Actual `_run_loop` checks cancellation, agent budget, iteration cap,
then `exit`, then `error`. If the last budgeted agent sets `exit=True`, the next

Evidence: full manager loop read. No production occurrence established and no
behavior change made. Proposed repair: define precedence and cover completion
exactly at each budget boundary before reordering the checks.


## Work-object follow-up (2026-09-19)

The original audit corrected documentation only; later repair statuses are marked per entry. Stronger
promises from the old comments are preserved here for later implementation work.
These are code-path findings, not claims of observed production incidents. See
[coverage and checks](structure_map_work_objects_2026-09-19.md). The non-exclusive
same-status dispatch claim is already LIVE 3 above and is not a new finding.

### WO1. Result recording is only partly epoch-fenced — FIXED for result commits; broader worker-write fencing remains

Intended: a stale result cannot alter its successor, and completion always has its
evidence. Actual `record_tool_result` loads once, may dispatch-hop and attach a pod,
then fences `set_status`, then appends evidence in another transaction. A stale result
can attach its pod before being rejected; a crash after status commit leaves no result
evidence, and later retries skip ended nodes. Concurrent same-epoch recorders can also
pass the initial open check and append duplicate results. The method catches every
ValueError from the status write, not just stale epochs; False does not imply no writes.

Evidence: full recorder/store reads and an isolated execution of the actual recorder
against an in-memory WorkStore: expected epoch 0 versus current 1 returned False but
persisted the stale pod. No app bootstrap or production DB was used. Proposed repair:
a single store operation that checks incarnation and eligible state, then atomically
writes pod, outcome and evidence, with an explicit duplicate-result policy.

### WO2. The audit log cannot rebuild graph state — OPEN

Intended: events are authoritative and the graph is replayable. Actual `apply` logs
original input data; generated goal/node/edge/action IDs and implicit cascade results
are not fully captured. There is no replay method in WorkStore. Boot migrations and
closure repair also write graph state outside ordinary mutation events.

Evidence: full model/store/accessor reads; in-memory creation confirms its generated
goal ID is absent from event data. Proposed repair: choose a complete deterministic
event contract and replay verification, or explicitly adopt graph state plus audit log
as the permanent persistence design. Current docs describe the latter behavior.

### WO3. Graph validation does not enforce the promised contract — FIXED for new writes; historical validation remains

Intended: acyclic dependency graph, inherited authority ceilings and validated lifecycle
entry. Actual validation checks ownership cycles and edge endpoints, but permits
self/duplicate/cyclic dependencies. `add_node` compares explicit authority only against
an explicit immediate-parent value; a parent with None bypasses an ancestor ceiling.
Initial status strings bypass transition and reason checks. Budget/deadline/approval
fields are metadata in this writer, and actor/licensed are caller-supplied assertions.
This finding does not establish a bypass of the separate tool execution scope gates.

Evidence: full model/store/tools reads; in-memory probes accepted a dependency cycle,
authority 99 below an authority-1 ancestor through a None parent, and a newly created
closed node without a reason. Proposed repair: define creation validation, effective
inherited authority, dependency constraints and the trusted writer boundary before
adding enforcement. Preserve legitimate same-status metadata updates (LIVE 3).

### WO4. Closure can disagree with the goal and miss ask-only repairs — PARTLY FIXED; historical repair held

Intended: container closure has a consistent goal state and repairs all closure zombies.
Actual `_rollup` changes only a dispatched goal to done before cascading startable nodes.
A proposed goal with satisfied children becomes abandoned while its container and final
epitaph say done. `repair_terminal_zombies` selects terminal containers with startable
nodes, omitting a container whose only remaining in-flight node is a user_reply ask,
even though the cascade helper would abandon that ask if invoked.

Evidence: full model/store reads; an in-memory object with a proposed goal and one
born-closed child produced container done / goal abandoned. Repair selection verified
by its SQL and cascade predicate. Proposed repair: define goal mirroring for all closure
entry points and align repair selection with the cascade's complete predicate.

### WO5. Legacy standalone driver no longer meets the dispatch contract — FIXED locally

Intended: `drive_work` advances a standalone graph to completion. Actual automatic
branch selects ready nodes but calls `discharge_node` without first claiming them;
that callee requires dispatched and raises. The explicit-node branch also requires a
preclaim, and neither branch invokes finalization. Evidence: full discharge module
read, including both caller and callee. Proposed repair: use the standard dispatch /
record / finalize lifecycle for scenarios, or retire the obsolete automatic helper.

### WO6. UI object-abandon action always lacks the required reason — FIXED locally

Repair: the endpoint supplies "owner abandoned via /work". A Flask route regression
checks HTTP 200, the persisted reason and the unstarted-child cascade. Running threads
are still not cancelled by this endpoint. Not yet published.

Intended: the manual editor can abandon an object through the validated writer.
Actual `api_work_abandon` sends only work_id and status; `_op_set_work_status` requires
a nonempty reason. `_apply` converts the resulting ValueError to HTTP 400. Evidence:
full blueprint/store reads and an in-memory execution of the same store request.
Proposed repair: supply an explicit user/manual-action reason. Do not imply graph
closure cancels a running worker or ticket; that requires a separate lifecycle policy.

### WO7. Store setup can conceal live-store failures — FIXED locally

Intended: UI dev fallback is for an unavailable app, and successful initialization
means migrations succeeded. Actual `_get_store` catches any live-store exception and
opens WORK_DB; the accessor's two migrations log and swallow errors before the singleton
may be cached. This can show a different DB or continue with unmigrated rows.

Evidence: full UI/accessor reads. Proposed repair: limit dev fallback to an explicit
standalone mode and define which migration errors must block initialization. Preserve
`store.path` reporting (LIVE 1 was already fixed).

### WO8. Wake metadata does not guarantee a real readiness gate — FIXED locally

Intended: deferred nodes carry a usable revisit condition. Actual `defer_node` validates
wake-kind vocabulary but not required time/reference combinations. Generic `is_ready`
checks status, future wake_at and dependencies only; a waiting event/signal reference
does not itself keep a node unready. Higher-level matching must supply that policy.

Evidence: full model/store/tool reads; an in-memory node with an unfulfilled event
reference and no future timestamp was ready. Proposed repair: define the division
between generic readiness and wake matching, validate required wake fields, and audit
callers before changing the predicate. No claim that this probe caused a production
redispatch is made.


### WO9. Invalid deferred timestamps can make a graph unreadable — FIXED locally

Repair: defer_node validates ISO strings/datetime values before assignment, accepts
null to clear the wake, and treats naive timestamps as UTC, matching persistence
conventions. Regressions assert malformed input leaves both graph and events unchanged,
and cover UTC/offset/naive round trips and clearing. This prevents new invalid writes;
it does not repair existing malformed rows. No schema migration. Not yet published.

`_op_defer_node` assigns `data["wake_at"]` directly onto an existing WorkNode.
Assignment is not Pydantic-validated; structural validation does not check timestamps,
and `_iso` persists an invalid string as supplied. A subsequent `WorkStore.load`
reconstructs the Pydantic model and raises ValidationError. One malformed defer can
therefore commit successfully and prevent normal reads and later apply calls for that
work object. This is stronger than the missing wake-field checks in WO8.

Evidence: model/store reads and an isolated in-memory probe: create an object, defer
its goal with wake_kind=time and wake_at=not-a-date; apply succeeds and the next load
raises ValidationError. No production data was touched. Proposed repair: parse and
validate wake timestamps before mutating/persisting, define timezone normalization,
and reject malformed input without committing an event or graph change.


## End-to-end Dayflow logic review (2026-09-19)

Evidence below is source tracing, not claims of observed production incidents or new
passing tests. All DF findings are OPEN. The full flow, boundaries and repair order are
in `dayflow_end_to_end_review_2026-09-19.md`. Existing findings retain their status.

### Existing findings: additional integration evidence

- **LIVE 3 (held decision):** dispatch's `_claim` is a same-status-capable `set_status`,
  not a compare-and-set claim. `open_session` registers by work/node, not incarnation.
  Do not describe either as exclusive. `work_node_dispatch_node` also accepts a qualified
  model-produced reference without proving membership in the offered candidates.
- **WO1:** normal `DayflowToolCaller.action_handler` ignores the boolean returned by
  `record_tool_result`, then enters `WorkFinalizerNode`. Recovery checks that boolean.
  Finalizer lookup and `_apply` carry no expected epoch/state; a delayed judgment can
  act on a successor (e.g. fail a newly dispatched attempt). Its multi-write retry
  sequence is also interruptible. `node_result` combines evidence from all attempts,
  without epoch selection. `sweep_stuck_work_nodes` and dispatch `_fail_node` likewise
  fail a node from a prior observation without incarnation/state comparison. A fenced
  recorder alone will not repair this lifecycle. Repeated-failure escalation also uses
  the pre-LLM goal count, so concurrent judgments can both miss the threshold.
- **WO8 / WO9:** the WO9 store validation repair remains valid, but architect `_to_dt`
  converts invalid timestamps to None before the store sees them, removing the time gate
  (DF6). This is a distinct caller defect, not proof that end-to-end deferred execution
  is fixed. State mover `_apply_node_wakes` accepts refs outside its offered waiting set,
  includes user_reply, and lacks a status/epoch guard; clearing a dispatched wait and
  restoring dispatched with evidence can create another epoch. `_park_held` retains
  user_reply on legacy asks, while the precise scheduler arms only time wakes.

### DF1. Restart recovery does not match the normal ticket producer — FIXED locally (2026-09-19; limitations below)

`work_session.re_arm_inflight_asks` queries suggestion_type=work_notify, within 48 hours
and 200 rows. Normal `DayflowSwitchboardArgumentsNode` supplies a brief, and
`CreateDayflowTicketTool._format_brief` obtains a free category from ticket_builder
(default general); the composer form describes logistics/wellness/scheduling categories.
No deterministic work_notify assignment connects these paths. Normal asks can therefore
be invisible to restart recovery, leaving dispatched nodes for the inactivity sweeper.
The new path also does not stamp wake_kind=user_reply or record the ticket as a work
object action, despite ask-cascade/action-history documentation relying on those fields.
Repair the producer/consumer contract using durable call identity, not model category.

### DF2. Ticket construction drops its graph context — FIXED locally (2026-09-19; limitations below)

`CreateDayflowTicketTool.execute` calls `_format_brief(args["ticket_brief"])`, although
that helper accepts work_node_ref and uses it to give ticket_builder the graph reference.
The dispatch arguments contain trigger_context.work_node but do not forward it here.
A delivery node saying to tell the user a previous step's result can reach the composer
without that result or its lookup reference. Optional research links do not cover general
worker results. Pass the canonical node context through the actual call boundary.

### DF3. Worker provenance exposed as schedulable work — FIXED locally

Repair: `is_work_unit` consistently limits orchestration to direct task children of
the goal. Promotion, waits/wakes, dispatch/session/recovery and supervision exclude
provenance, including previously actionable records. Architect references cannot name
provenance. Worker/finalizer views include full owned history; strategic views show
finalizer summaries. UI labels provenance explicitly. No schema or historical-row
migration. Eleven focused regressions cover this boundary; the Dayflow suite passes
371 tests after updating superseded expectations. No live rollout or push.

User-confirmed ownership contract: worker-created descendants are internal helper
records for the assigned main node, not independently schedulable work. The architect
and steward must never assign an agent to them. Their persistence in the same nodes
table does not grant the orchestrator execution ownership. Missing parent dependency
edges are not the defect and adding them is not the proposed repair. The defect below
is that candidate generation does not enforce this boundary before offering helpers
to the action selector. Actual duplicate execution still requires a concurrent tick
and selection of an exposed helper; no production occurrence was established here.

`ManagerInterface._run_on_child_node` creates a proposed subtask and runs its manager
synchronously without claiming it. `WorkPlanner._reconcile_to_graph` also creates
proposed checklist children. Both state-mover promotion and materialization iterate
all depths; neither excludes descendants of a running worker. The planning gate does
not lock dispatch threads. During a child call, another tick can promote and dispatch
that same child, duplicating work/side effects; queued checklist work can also run out
of the worker's chosen order. The interface comment that nothing can race is false.
Enforce top-level scheduler ownership and explicit nested execution ownership together.

### DF4. A failed finalizer strands recorded results — FIXED locally (2026-09-19)

`WorkFinalizerNode.action_handler` catches judgment/write failures; an unusable verdict
returns an empty result. A tool result already recorded as done stays done. Boot ask
recovery and the inactivity sweeper select dispatched nodes, and planning has no
finalizer stage. There is no deterministic retry of this unjudged result. A crash
between recording and finalizing has the same consequence. Steward intervention is
not recovery of the missing judgment. Persist/rediscover pending adjudication, and
retry judgment without executing the external tool again.

### DF5. Pending replans do not prevent execution — FIXED locally (2026-09-19)

Finalizer retry writes failed then proposed. Architect handles at most three replan
objects per tick and catches per-object errors. State mover subsequently promotes ready
nodes regardless of pending finalizer instructions. A deferred/failed replan can thus
redispatch the unchanged failed step. achieved_plan_changes closes a node and unblocks
dependents before the pending graph revision is applied. Hold affected execution until
the exact instruction has been successfully applied, including replans arriving during
the planning pass.

### DF6. Architect application can expose an incomplete or ungated plan — FIXED locally (2026-09-19; limitations below)

`apply_architect_dag` commits prunes, additions, edges and wakes separately; its caller
logs errors and continues to promotion. An error after additions can leave runnable
nodes missing dependencies/wakes. Missing dependency IDs are silently skipped.
`_to_dt` logs malformed times and returns None, allowing immediate execution instead
of rejecting the plan. Validate the complete delta first and publish it atomically,
or use an explicit non-dispatchable construction state with recovery.

### DF7. Replan acknowledgement can consume the wrong verdict — FIXED locally (2026-09-19)

`WorkArchitectNode` snapshots pending instructions before its LLM call, then consumes
by work_id/node_id only. `_op_consume_finalizer_instruction` stamps whichever finalizer
payload exists at write time. A new verdict during the call can be acknowledged without
being planned. Separately, refused prunes are swallowed by `apply_architect_dag`, so
its return is not proof that the requested revision succeeded, yet instructions are
consumed. Compare instruction identity/version and acknowledge only applied changes.

### DF8. Deduplicating a node leaves its dependents attached to the discarded copy — FIXED locally (2026-09-19)

`apply_architect_dag` validates a surviving twin and abandons the duplicate, but does
not redirect depends_on edges. `WorkObject.is_ready` requires each named dependency to
be satisfied; an abandoned tool-success subtask is not. A downstream node can remain
blocked after the surviving twin succeeds. Rewire/validate affected dependencies as
part of the same revision. This is distinct from general dependency validation (WO3).

### DF9. Admitted intake has no durable evaluator inbox — FIXED locally

Triage persists ADMIT as artifact. `IntakeTriagePrepNode` offers new items, while the
active evaluator config consumes this tick's admitted_artifacts, not an outstanding
admitted backlog. Failure after admission but before work creation can strand actionable
intake outside later evaluator inputs. Existing artifact display in triage is not a
reliable evaluator handoff. The same gap affects admitted work deliberately left for
later. Keep admitted-unconsumed intake in the evaluator's durable input set.

### DF10. Intake handoff loses source detail at creation/change boundaries — FIXED locally for durable source handoff

`StrategicPlannerWoPersistNode._fold_intake_into_goals` stores source summaries/pod IDs
in goal.content, but catches failures; `_close_consumed_items` closes items anyway.
Initial `WorkArchitectNode` receives created["objective"] plus rationale and a portfolio
built before creation, not the enriched goal. Thus even a successful fold does not
supply the first architect with the promised source handles. Later `persist_steward_output`
changes replace goal.content with objective, removing folded provenance. Preserve source
context separately, pass the stored goal on creation, and close intake only after a
successful durable transfer. Partial creation failure also discards the returned created
list in the persist node, leaving already-created goals without this tick's decomposition.

### DF11. Ticket publication can race reply-listener registration — FIXED locally (2026-09-19; limitations below)

`CreateDayflowTicketTool.execute` publishes the suggestion (and optionally TTS) before
`_wait_for_ticket_response` registers its listener. The normal wait does not re-read
the durable ticket after registration or timeout. A response in the gap can therefore
be recorded in the DB but reported to the graph as timeout. Recovery's extra read
corrects the result only after waiting out the timeout. Register/reconcile against the
stored ticket so an already-arrived answer completes promptly. This is separate from
LIVE 4a's already-fixed handling of a genuinely late reply.

### DF12. Recovery tickets are not bound to dispatch incarnation — FIXED locally (2026-09-19; limitations below)

`re_arm_inflight_asks` chooses the newest ticket by node reference and records it using
the node's current epoch. The ticket binding contains no captured dispatch epoch. If
an earlier attempt has a settled ticket and a successor crashes before minting its own,
boot can apply the old answer to the new attempt. Session IDs also omit incarnation.
Persist the ticket/call association and recover only the matching attempt (WO1 related).

### DF13. A hold during a precise wake has no replacement precise wake — FIXED locally (2026-09-19; limitations below)

`DayflowScheduler._fire_work_node` invokes the wake manager and returns. If state mover
parks the node at a new reactivate_at, `_arm_work_node_wakes` is not called there; it
runs after planning ticks only. The consumed one-shot job has no replacement until
another tick, potentially the 30-minute ceiling. Re-arm the new due time after a wake
pass, including failure handling. Stale per-node jobs are not removed when gates change;
callback checks do not establish that the original time gate still applies.

### DF14. Scheduler stop leaves timed execution jobs alive — FIXED locally (2026-09-19; limitations below)

`DayflowScheduler.stop` removes the main JOB_ID only. Per-node jobs installed by
`_arm_work_node_wakes` remain; `_fire_work_node` does not check _started. Calling stop
while the timing engine continues can still invoke a wake manager and dispatch work.
Remove the owned jobs and guard callbacks, including jobs already waiting for the gate.

### DF15. Cadence overwrites newly written watermarks and chat blocking — FIXED locally (2026-09-19; limitations below)

`dayflow_orchestrator_cadence_tick` loads status before ingestion, then persists that old
dict after manager invocation. Ingestion writes chat/pod watermarks into the same resource.
`load_orchestrator_status` returns a copy and `ResourceManager.update_resource` replaces
the value; it does not merge. Successful ticks overwrite their new cursors. Master-room
blocking updates made while the manager runs can be lost too. Use synchronized field
updates rather than a long-lived whole-resource snapshot. Persistence file errors are
also logged/swallowed by ResourceManager, so return does not prove durable status.

### DF16. Ingestion advances cursors before saving intake — FIXED locally (2026-09-19; limitations below)

`ingestion._ingest_chat` and `_ingest_pods` persist their watermarks before
`run_dayflow_ingestion` writes its destination batch. A later source/write failure or
process crash leaves cursors beyond missing intake. The old-snapshot overwrite in DF15
sometimes hides this on successful ticks; it is not recovery after an interrupted tick.
Commit items before advancing, with idempotent restart or a transactional cursor design.

### DF17. Bounded source queries can skip or starve intake — FIXED locally (2026-09-19; limitations below)

Pod ingestion asks `PodStore.query` for 200 newest rows, filters kinds afterwards, then
advances to the newest matching timestamp. Older unprocessed eligible pods can be left
behind the cursor. Chat ingestion takes 500 ascending rows before Python noise/mode
filtering: 500 excluded rows can yield no messages and no cursor progress, repeatedly
hiding later legitimate chat. Timestamp-only `>` pagination can also skip rows sharing
a batch-boundary timestamp; failed row conversion can be skipped once a later row
advances the cursor. Use stable paginated cursors and explicit failure disposition.
DF15's rewind can mask some cursor progression symptoms while causing repeated scans.

### DF18. Delegation ingestion acknowledgement is not repaired after a crash — FIXED locally (2026-09-19; limitations below)

`_ingest_delegation_requests` returns raw requests to acknowledge only when their item
IDs are new. If the batch commits but marking the requests ingested fails, subsequent
runs deduplicate them and never retry that acknowledgement. The request remains pending
until some separate lifecycle cleanup. Reconcile existing destination IDs as successful
handoffs too; do not recreate the work just to acknowledge the request.

### DF19. Short intake IDs can collide after the reset threshold — FIXED locally (2026-09-19; limitations below)

`run_dayflow_ingestion` resets max(existing short_id)+1 to 1 at 10000 without checking
existing occupancy. Subsequent batches can keep resetting while older maximum IDs
remain. Triage and consumption accept short IDs via maps, so two live artifacts can
become ambiguous or the wrong one can be consumed. Use unique stable references or an
allocator that excludes every still-addressable ID. This verifies the collision mechanism
behind historical comments about duplicate short IDs; no production count was measured.

### DF20. Finalizer directive and evaluator success criteria — FIXED locally for directive and criteria delivery

The finalizer now receives full node.content, its success-condition kind and the full
owned provenance history, alongside the returned result. The prompt tells it to summarize
attempts, failures, accomplishments and unresolved work for the strategic agents. The
separate evaluator success_criteria persistence gap below remains OPEN.

`WorkFinalizerNode._judge` sends full result text and node.title. Its task is
`render_work_portfolio`, whose subtask rows use `_t` (title first, capped at 90 chars),
not the node's full content. The goal's full content is present, but the particular
step's detailed constraints are absent. A plausible result can be judged achieved
without checking the actual instruction. Include immutable node content and explicit
success conditions alongside the attempt's result. Evaluator `success_criteria` is also
emitted by WorkObjectSpec but never persisted by `persist_steward_output`; this loses
criteria that were not repeated in objective.

### DF21. Returned manager failures are not treated as failed runs — FIXED locally (2026-09-19; limitations below)

Cadence ignores its manager ToolResult; scheduler health records ok unless an exception
escapes. `_run_dispatch_session` likewise ignores its manager result; an aborted dispatch
before recording can leave the node dispatched until the inactivity sweep. Internal
control nodes often log and continue, further masking incomplete stages. Interpret the
manager's exit contract and report the failed stage; preserve the distinction between
re-running a tool and retrying result/finalizer persistence. See R2/R5 for shared envelope
problems rather than duplicating them here.

### DF22. Queued nodes bypass a fresh readiness check — FIXED locally (2026-09-19)

`WorkNodeMaterializerNode._node_items` tests actionable only, not current dependencies
or time/event gates. Dispatch `_claim` does not recheck them either. If a replan adds a
dependency to an already-actionable node, it can still execute before that dependency.
Promotion validated an earlier graph, not the graph being dispatched. Validate readiness
and eligible ownership atomically with the actual claim (LIVE 3/WO8 related).

### DF23. Internal failures inflated the main goal failure count — FIXED locally

`_count_unmet_attempt` previously counted every non-goal record entering failed. A
worker's internal unsuccessful attempt could therefore increase goal_unmet_attempts

### MEM1. Noticer belief updates are logged and counted, never applied — OPEN (P1)

### MEM2. Ticket outcomes are converted into stronger user-intent claims — OPEN (P1)

The aggregate collector maps expired to snoozed and emits “User snoozed/deferred ... without completing.” It also maps accepted to acceptance without reading the contextual response meaning, scope or typed text introduced by DF36.
